# FlowRun v0.3 Unattended CLI Bridge Design

## Product goal

FlowRun v0.3 lets a developer submit a validated workflow from the terminal to an already-open ChatGPT conversation and then walk away. After the job is durably accepted by the extension, the CLI is not the workflow controller: the extension owns execution and continues locally even if the terminal closes or the CLI process exits. Chrome must remain open and the computer must remain awake; v0.3 does not wake a sleeping Mac or launch Chrome after shutdown.

The queue panel also gains a lightweight loading animation whenever normal Queue or FlowRun execution is actively running. The animation stops for Idle, Paused, Blocked, Completed, and Failed states.

## Non-negotiable constraints

- No cloud service, telemetry, localhost HTTP/WebSocket server, or API key.
- No arbitrary shell execution from a workflow or bridge request.
- Normal queue sending still flows only through QueueCoordinator -> QueueRunner -> DOMChatGPTAdapter.
- CLI exit, terminal close, or Ctrl+C after acceptance must never cancel or duplicate a submitted workflow.
- Ambiguous browser delivery remains fail-closed; no automatic prompt retry.
- Bridge requests are bounded, versioned, authenticated by Chrome Native Messaging allowed origin plus a local per-install bridge secret.
- A bridge job ID is idempotent. Re-delivery of the same job must return existing state and must not start a second workflow.
- Multiple open ChatGPT conversations are explicit targets. If more than one eligible target exists and --target is omitted, CLI fails closed.
- Chrome must remain open and the target ChatGPT tab must remain available. If the tab/content script reloads during an active workflow, existing v0.2 browser-session-interrupted behavior remains fail-closed.
- Base Queue usage must not require nativeMessaging permission. The permission is optional and requested only when the user enables the CLI bridge.

## Architecture

### Durable ownership model

The CLI is a submitter, not a runtime controller.

1. CLI validates the workflow and writes a durable request to `~/.flowrun/bridge/inbox/<jobId>.json` using atomic rename.
2. A Chrome Native Messaging host, spawned by the extension, polls the inbox and forwards requests to the extension service worker.
3. The service worker validates protocol/version/size/secret and persists a bridge job record in `chrome.storage.local` before acknowledging acceptance.
4. The service worker routes the accepted job to the selected registered ChatGPT content script.
5. The content script executes through the existing FlowRunBrowserController and queue runtime.
6. Run/job state is persisted to `chrome.storage.local`. The native host mirrors event snapshots/results to `~/.flowrun/bridge/events/` and `results/` for CLI inspection.
7. The CLI may follow these files, detach immediately, be interrupted, or exit. None of those actions change extension execution.

The durable acceptance boundary is the extension bridge-job repository write. CLI must print `accepted` only after it observes an acceptance event/result associated with the exact job ID.

## Native Messaging host

Host name: `com.senoldogan.flowrun`

V0.3 targets macOS Chrome developer installs. `flowrun bridge install --extension-id <id>` installs:

- `~/.flowrun/bridge/bin/flowrun-native-host.js`
- a small executable launcher using the current Node executable
- `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.senoldogan.flowrun.json`
- `~/.flowrun/bridge/config.json`

The native-host manifest contains exactly one `allowed_origins` entry for the supplied extension ID. The installer generates a random local bridge secret and stores it in `config.json` with user-only file permissions where supported.

No daemon or listening socket is installed. Chrome starts the native host through Native Messaging. The host uses stdin/stdout only for Chrome protocol frames and the local mailbox only for CLI handoff/status.

## Extension permission and connection

`manifest.json` adds `optional_permissions: ["nativeMessaging"]`; the existing required permissions stay unchanged.

The Queue panel exposes a compact developer control:

- `Enable CLI bridge` when optional permission is absent.
- `CLI bridge enabled` when permission is granted and a native host connection has been established.
- concise disconnected/missing-host error when permission exists but host is unavailable.

The permission request occurs only from an explicit user click.

Once enabled, the service worker calls `chrome.runtime.connectNative("com.senoldogan.flowrun")`. Content-script registration/heartbeat messages opportunistically reconnect the port after service-worker restarts. No new `tabs` permission is required; the service worker routes only to tab IDs learned from content-script senders.

## Target registry

Each ChatGPT content script periodically registers:

```ts
interface BridgeTargetRegistration {
  conversationKey: string;
  queueStatus: QueueStatus;
  workflowStatus?: WorkflowRun['status'];
}
```

The service worker associates the registration with `sender.tab.id`, never trusting a tab ID supplied by content-script payload. Registry entries are memory-only with a 30 second expiry and are refreshed by existing content-script heartbeat cadence.

`targets` responses expose an opaque target ID derived by the service worker, provider `chatgpt`, conversation key, and busy/available state. They do not expose page text, cookies, credentials, or conversation messages.

## Bridge protocol

Protocol version is `1`.

CLI mailbox request:

```ts
interface BridgeJobRequest {
  version: 1;
  jobId: string;
  secret: string;
  kind: 'targets' | 'run';
  createdAt: number;
  expiresAt: number;
  payload: TargetsPayload | RunPayload;
}
```

`RunPayload` contains the validated workflow document, explicit string inputs, and optional target ID. Maximum serialized request size is 1 MiB. Default request TTL is 10 minutes.

Extension job state:

```ts
type BridgeJobStatus = 'accepted' | 'running' | 'blocked' | 'completed' | 'failed';

interface BridgeJobRecord {
  version: 1;
  jobId: string;
  kind: 'run';
  targetId: string;
  conversationKey: string;
  status: BridgeJobStatus;
  workflowRunId?: string;
  error?: string;
  createdAt: number;
  updatedAt: number;
}
```

The extension repository keeps the 50 most recent bridge jobs. Duplicate job IDs return the persisted job instead of executing again.

Native host mailbox events are append-by-sequence JSON snapshots named `<jobId>.<sequence>.json`; final results are atomically written to `results/<jobId>.json`.

## CLI UX

Commands:

```text
flowrun bridge install --extension-id <chrome-extension-id>
flowrun bridge doctor
flowrun targets
flowrun run <workflow.json> --input key=value [--target <target-id>] [--detach]
flowrun status <job-id>
```

`flowrun run` validates locally first. It submits one durable request and waits only for acceptance. Without `--detach`, it then follows event/result files for progress. Ctrl+C after acceptance exits the CLI with a detached message but does not write cancellation state.

If zero targets exist, CLI reports that Chrome/ChatGPT/bridge must be open. If exactly one available target exists, it is selected automatically. If multiple targets exist, `--target` is required. Busy targets fail closed.

## Unattended behavior

After a run job reaches `accepted`, execution no longer depends on the CLI process or native host remaining continuously alive. The extension has the job and FlowRun run in Chrome local storage. Native host disconnect/reconnect affects only CLI visibility, not execution.

If Chrome remains open and the computer awake, normal queue/FlowRun execution continues using current background-tab reliability logic. If Chrome closes, the Mac sleeps, the target tab reloads, or ChatGPT presents an ambiguous/error state, execution does not guess. Existing fail-closed state is persisted and can be inspected later.

V0.3 explicitly does not implement OS wake scheduling, auto-launching Chrome, or remote mobile monitoring.

## Loading animation

The Queue header shows a small CSS-only spinner beside `Running` when either:

- queue status is `running`, or
- current FlowRun status is `running`.

No JavaScript animation timer is used. This avoids new render churn. The spinner uses `prefers-reduced-motion: reduce` to disable rotation while keeping a static activity indicator.

The collapsed right-edge tab also shows the activity spinner while running so unattended state is visible without expanding the panel.

## Security and cleanup

- Native request body hard cap: 1 MiB.
- Job TTL: 10 minutes before acceptance; expired inbox requests are moved to a rejected/final result rather than executed.
- Local mailbox writes use temp-file + atomic rename.
- Filenames use validated UUID-like job IDs only; no caller-controlled paths.
- Native host ignores unknown protocol versions and malformed frames.
- Bridge secret uses at least 32 random bytes and constant-time comparison in the native host/extension validation layer where applicable.
- Host manifest accepts only the configured extension origin.
- `bridge doctor` checks paths, manifest, secret/config shape, and whether the CLI can create/read mailbox files. It does not send a workflow.
- Old mailbox event files are cleaned by bounded age/count policy; bridge job repository keeps 50 records.

## Testing

### Unit/integration

- mailbox atomic submit/read/result behavior
- request size, TTL, secret and version validation
- bridge repository idempotency and 50-job bound
- target registry expiry and sender-tab identity
- duplicate run request cannot start a second FlowRun
- CLI target selection: 0/1/many and busy target behavior
- CLI run validates before submit and detaches safely
- bridge installer/doctor paths via injected filesystem/platform adapters
- UI optional-permission state and loading indicator rendering
- reduced-motion CSS exists and no JS spinner timer exists

### Browser E2E

Use a deterministic fake native-port adapter in extension E2E rather than requiring OS Native Messaging installation in CI:

1. Register two ChatGPT fixture tabs and verify target selection metadata.
2. Submit one run bridge job to a target.
3. Observe acceptance before execution.
4. Close/detach the simulated CLI side.
5. Verify two-step workflow completes anyway.
6. Re-submit identical job ID and verify no duplicate ChatGPT sends.
7. Verify running spinner appears during queue/workflow execution and stops on completed/blocked/paused.

Native host framing/mailbox tests run in Node separately.

## Success criteria

V0.3 is complete when a developer can install/doctor the local bridge, list active ChatGPT targets, submit a workflow from CLI, terminate the CLI after acceptance, and observe the workflow finish through the extension without duplicate dispatch; the queue header visibly animates only while active execution is running; all prior Queue and FlowRun tests remain green; required extension permissions remain `storage` and `notifications` with `nativeMessaging` optional only.
