# FlowRun v0.1 Design

## Product thesis

FlowRun turns the existing ChatGPT Queue extension into a developer-grade, local-first workflow runtime for AI web applications. The product is not another prompt queue. Its differentiator is deterministic browser execution with fail-closed safety, recoverable run state, receipts, assertions, and provider adapters that use the user’s existing web session rather than an API key.

The long-term positioning is: **Playwright-style reliability for AI workflows running through the web apps developers already pay for.**

## Scope of v0.1

V0.1 deliberately implements only the reusable core required to prove the product direction without destabilizing the production extension.

V0.1 includes:

1. A versioned workflow document schema.
2. Workflow parsing and validation.
3. A deterministic workflow run model with append-only events.
4. Template interpolation for declared inputs and previous step outputs.
5. A provider-agnostic chat-step execution contract.
6. Dry-run planning that resolves dependencies and prompts without sending anything.
7. Run inspection and receipts.
8. A CLI with `validate`, `dry-run`, and `inspect` commands.
9. A bridge boundary that allows the existing ChatGPT browser runner to become the first provider in a later milestone without rewriting its safety state machine.

V0.1 does **not** include remote sync, billing, team features, a visual workflow builder, Claude/Gemini adapters, arbitrary shell execution, autonomous loops, secrets management, or live CLI-to-extension transport. Those are later milestones.

## Workflow document

The workflow file is JSON in v0.1. YAML is deferred until the schema stabilizes so the first release adds no parser dependency. The schema is intentionally small.

Example:

```json
{
  "version": 1,
  "name": "review-pr",
  "inputs": {
    "diff": { "type": "string", "required": true }
  },
  "steps": [
    {
      "id": "architecture",
      "type": "chat",
      "provider": "chatgpt",
      "prompt": "Review this diff architecturally:\n{{ inputs.diff }}"
    },
    {
      "id": "bugs",
      "type": "chat",
      "provider": "chatgpt",
      "prompt": "Using this review:\n{{ steps.architecture.output }}\nFind concrete bugs only.",
      "assert": [
        { "type": "output_not_empty" }
      ]
    }
  ]
}
```

### Schema rules

- `version` must be exactly `1`.
- `name` must be a non-empty slug-like identifier matching `[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}`.
- Input names and step IDs use the same identifier rule.
- Step IDs must be unique.
- V0.1 supports only `type: "chat"` steps.
- `provider` is a non-empty identifier. The only built-in provider name is `chatgpt`, but the core does not hard-code ChatGPT behavior.
- `prompt` must be non-empty after trimming.
- Templates may reference `inputs.<name>` and `steps.<stepId>.output` only.
- A step may reference only an earlier step, never itself or a later step.
- Unknown top-level keys and unknown step keys are rejected to keep workflow behavior explicit.
- Maximum workflow size is 100 steps; maximum rendered prompt size is 200,000 UTF-16 code units.

## Core runtime model

FlowRun separates immutable workflow definition, mutable run state, and provider execution.

### Run state

```ts
interface WorkflowRun {
  id: string;
  workflowName: string;
  workflowVersion: 1;
  status: 'pending' | 'running' | 'blocked' | 'completed' | 'failed';
  inputs: Record<string, string>;
  steps: StepRun[];
  events: RunEvent[];
  createdAt: number;
  updatedAt: number;
}
```

Each `StepRun` has its own state:

```ts
type StepRunStatus =
  | 'pending'
  | 'ready'
  | 'dispatching'
  | 'waiting'
  | 'completed'
  | 'blocked'
  | 'failed';
```

### Events

The event log is append-only. Events are the audit trail and the source of receipts.

V0.1 event kinds:

- `run.created`
- `run.started`
- `step.ready`
- `step.dispatch_reserved`
- `step.dispatch_confirmed`
- `step.output_captured`
- `step.assertion_passed`
- `step.assertion_failed`
- `step.completed`
- `run.blocked`
- `run.failed`
- `run.completed`

Every event has `id`, `runId`, `at`, `kind`, `stepId?`, and a JSON-serializable `data` object.

## Provider contract

The core runtime never touches the DOM. Providers implement a narrow contract.

```ts
export interface ChatProvider {
  readonly id: string;
  execute(request: ChatExecutionRequest): Promise<ChatExecutionResult>;
}

export interface ChatExecutionRequest {
  runId: string;
  stepId: string;
  prompt: string;
  dispatchToken: string;
}

export type ChatExecutionResult =
  | { kind: 'completed'; output: string; receipt: ProviderReceipt }
  | { kind: 'blocked'; reason: string; receipt?: ProviderReceipt };
```

A `ProviderReceipt` is provider-neutral metadata such as `provider`, `dispatchToken`, timestamps, and optional conversation identity. It must never contain credentials.

The existing ChatGPT Queue state machine remains the browser-safety implementation. A later adapter will translate one FlowRun chat step into the existing reserve/send/generation/completion lifecycle rather than duplicating it.

## Deterministic execution

The engine executes steps in document order in v0.1. No branching or parallelism is allowed yet.

For each chat step:

1. Resolve the prompt template from declared inputs and completed earlier step outputs.
2. Append `step.ready`.
3. Create a random `dispatchToken` and append `step.dispatch_reserved` before calling the provider.
4. Invoke the provider exactly once for that reservation.
5. If the provider blocks, mark the run blocked and stop.
6. If the provider completes, append `step.dispatch_confirmed` and `step.output_captured`.
7. Evaluate assertions.
8. On assertion failure, append `step.assertion_failed`, fail the run, and stop.
9. Otherwise append `step.completed` and continue.
10. After the final step, append `run.completed`.

The engine never retries a provider dispatch automatically. Retry/recovery semantics require a future persisted live browser bridge and must preserve the existing fail-closed rule.

## Assertions

V0.1 includes two deterministic assertions:

```ts
type StepAssertion =
  | { type: 'output_not_empty' }
  | { type: 'output_contains'; value: string };
```

`output_contains` is a case-sensitive substring assertion in v0.1.

## Template engine

Templates use exactly two forms:

- `{{ inputs.name }}`
- `{{ steps.stepId.output }}`

The renderer rejects unresolved, malformed, or unauthorized expressions. There is no code execution, condition language, function invocation, or environment-variable access.

## CLI

The v0.1 executable is `flowrun`.

Commands:

```text
flowrun validate <workflow.json>
flowrun dry-run <workflow.json> --input key=value [--input key=value ...]
flowrun inspect <run.json>
```

### `validate`

Validates syntax and semantics. Success prints a compact summary and exits `0`; invalid workflows print actionable errors and exit non-zero.

### `dry-run`

Validates the workflow and inputs, renders every step that can be resolved using synthetic placeholder outputs for earlier steps, and prints the execution plan. It never invokes a provider and never writes browser state.

### `inspect`

Reads a serialized `WorkflowRun`, validates the run shape enough to report safely, and prints status, per-step state, and a receipt/event timeline.

V0.1 intentionally does not implement `flowrun run` until the live extension transport is designed and proven. This avoids creating a misleading CLI that claims to execute browser workflows without a safe transport.

## Repository layout

The project remains one npm package for v0.1 to avoid premature monorepo complexity.

```text
src/flowrun/
  schema.ts          workflow types and validation
  template.ts        safe interpolation
  events.ts          event types and event creation
  engine.ts          deterministic sequential workflow engine
  provider.ts        provider contract and receipts
  assertions.ts      deterministic assertions
  inspect.ts         inspection/receipt formatting data

src/cli/
  flowrun.ts         argument routing and exit codes
  io.ts              filesystem/stdin-safe helpers for CLI

tests/flowrun/
  schema.test.ts
  template.test.ts
  engine.test.ts
  assertions.test.ts
  inspect.test.ts
  cli.test.ts
```

The current queue extension code remains under its existing directories. V0.1 does not rename or move production extension modules.

## Error model

Validation errors are structured as `{ code, path, message }` and may contain multiple errors at once.

Runtime failures use explicit states. Programmer errors may throw, but expected workflow errors do not rely on stringly-typed exceptions.

Important error codes include:

- `workflow.invalid_version`
- `workflow.invalid_name`
- `workflow.unknown_key`
- `workflow.too_many_steps`
- `step.duplicate_id`
- `step.invalid_provider`
- `step.empty_prompt`
- `template.invalid_expression`
- `template.unknown_input`
- `template.future_step_reference`
- `input.missing_required`
- `assertion.failed`
- `provider.blocked`

## Security and privacy

- FlowRun core performs no network requests.
- Workflow templates cannot evaluate arbitrary JavaScript.
- Inputs are strings only in v0.1.
- The CLI does not read environment variables implicitly.
- Provider receipts must not store cookies, auth headers, session tokens, or prompt DOM snapshots.
- Existing extension permissions remain unchanged in v0.1.
- No telemetry is added.

## Testing strategy

All implementation follows TDD.

Required coverage:

- malformed workflow validation
- duplicate and forward-reference rejection
- exact template resolution
- missing input rejection
- deterministic sequential step order
- dispatch reservation before provider call
- provider-blocked fail-closed behavior
- no automatic retry
- assertion pass/fail behavior
- event ordering and receipts
- CLI exit codes and output
- regression: existing queue tests and all current Chromium E2E remain green

## Success criteria

V0.1 is complete when:

1. A developer can author a valid workflow JSON file and validate it with the CLI.
2. A developer can dry-run it with explicit inputs and see the rendered deterministic plan.
3. The core engine can execute the same workflow against a fake provider in tests and produce an inspectable run/event history.
4. Provider blocking stops execution without duplicate dispatch.
5. Existing ChatGPT Queue production behavior, permissions, unit tests, and browser E2E are unchanged and green.
6. The new core has no network dependency and no API-key concept.

## Next milestone after v0.1

V0.2 will design and implement the authenticated local bridge between `flowrun run` and the extension, with ChatGPT as the first live provider. That milestone must reuse the existing fail-closed queue lifecycle and preserve crash/reload/identity-migration guarantees.
