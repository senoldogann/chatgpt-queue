# FlowRun v0.2 Live Browser Runtime Design

## Product goal

FlowRun v0.2 turns the v0.1 deterministic workflow core into a real browser-executed workflow runtime inside the existing ChatGPT Queue extension. A developer loads a `.flowrun.json` workflow into the extension, provides required string inputs, and runs the workflow in the current ChatGPT conversation. Each chat step is executed through the existing fail-closed queue/state-machine path, the completed assistant response is captured locally, and that output becomes available to later `{{ steps.<id>.output }}` templates.

This slice does **not** add CLI-to-browser IPC. The CLI remains `validate`, `dry-run`, and `inspect`; live execution happens inside the extension. CLI live transport is deferred until the browser runtime is proven reliable.

## Non-negotiable constraints

- Reuse the existing ChatGPT queue runner and ownership rules. Do not create a second independent send loop.
- Never auto-retry a dispatch whose delivery state is ambiguous.
- Never skip a workflow step after a browser/DOM error.
- No telemetry, API keys, backend, websocket service, or external network calls.
- All workflow definitions, inputs, outputs, receipts, and run events remain local.
- Existing queue behavior and permissions stay unchanged.
- Only provider `chatgpt` is live in v0.2.
- A live workflow can start only when the current conversation queue has no queued, sending, or running items.
- Workflow execution is sequential.
- A reload/extension restart during an active workflow must not resend the active prompt automatically. The persisted run becomes blocked with `browser-session-interrupted` unless the underlying queue is already conclusively blocked for a more specific reason.

## Runtime architecture

### Existing layers reused

`QueueCoordinator` and `QueueRunner` remain the only components that reserve and send ChatGPT messages. The current DOM adapter remains responsible for page state, send control detection, completion evidence, blocking UI, and confirmation UI.

### New live execution layers

`FlowRunBrowserController` owns one live workflow run for the current content-script session. It validates that the queue is free, constructs a `BrowserChatProvider`, executes the existing `executeWorkflow()` engine, persists run snapshots/events through a `FlowRunRunRepository`, and publishes live run state to the UI.

`BrowserChatProvider` implements the existing `ChatProvider` contract. For one `execute()` call it:

1. Records the current assistant-turn identity baseline.
2. Adds exactly one queue item containing the rendered step prompt.
3. Starts the existing queue through the normal claim/start path.
4. Waits for that exact queue item to become `completed` or for the queue to become `blocked`.
5. Captures the latest completed assistant output associated with the new assistant turn.
6. Returns `completed` with a receipt/output, or `blocked` with the queue reason.

The provider never calls the DOM send button directly.

## Assistant output capture

The DOM adapter gains a provider-neutral read method that returns a completed assistant artifact:

```ts
interface AssistantArtifact {
  turnKey: string;
  text: string;
}
```

The artifact must come from the latest assistant conversation turn and must only be returned when completion evidence is present. Completion evidence is either:

- the assistant turn exposes a completion action such as `copy-turn-action-button`, or
- the queue runtime already observed generation and subsequently reached stable completion.

The adapter extracts visible assistant response text from the assistant message subtree and excludes extension UI, action buttons, and known hidden/non-content controls. Empty output is treated as `assistant-output-unavailable` and blocks the workflow.

The provider records the assistant turn key observed before dispatch and requires the captured post-step artifact to have a different turn key. This prevents reusing the previous answer as the output of a new step.

## Specific ChatGPT delivery timeout classification

`detectBlockingReason()` recognizes the current ChatGPT error text:

- `Message delivery timed out. Please try again.`

and Turkish-equivalent wording when present, and returns:

`message-delivery-timeout`

This remains fail-closed. v0.2 does not automatically press Retry and does not automatically resend the prompt.

## Run persistence

A new local storage namespace stores bounded FlowRun history separately from queue state.

```ts
interface FlowRunStoreState {
  version: 1;
  runs: Record<string, WorkflowRun>;
  order: string[];
}
```

Rules:

- Keep at most 20 runs.
- Save the run after every emitted event and final state transition.
- Never store extension ownership/tab IDs inside the workflow run document.
- The latest run can be displayed/inspected in the panel.
- On content-script attach, any persisted `running` FlowRun run associated with the current conversation is changed to `blocked` with a synthetic `run.blocked` event whose reason is `browser-session-interrupted`. No prompt is resent automatically.

`WorkflowRun` gains optional browser metadata:

```ts
browser?: {
  conversationKey: string;
}
```

This field is local metadata and remains optional so existing v0.1 CLI run documents stay valid.

## Extension UI

The existing Queue panel remains the primary surface. Add a compact `Workflow` section below the queue composer.

Idle state:

- `Load workflow` file input accepting `.json` and `.flowrun.json`.
- Loaded workflow name and step count.
- One text input per declared workflow input.
- `Run workflow` button.

Running state:

- workflow name
- current step id
- progress `N / total`
- status `Running`
- no second workflow can be started

Terminal states:

- `Completed`, `Blocked`, or `Failed`
- concise reason for blocked/failed state
- `Clear workflow` resets only the UI selection, not persisted history

A workflow run cannot start if normal queue items exist. The UI shows `Finish or clear the current queue before starting a workflow.`

## Data flow

1. User loads workflow JSON.
2. UI parses and calls `validateWorkflowDocument`.
3. UI gathers required string inputs.
4. Controller confirms current queue is idle and clean.
5. `executeWorkflow()` begins and emits events.
6. Controller persists each event snapshot.
7. Engine calls `BrowserChatProvider.execute()`.
8. Provider enqueues one rendered prompt through the existing queue API.
9. Existing queue runner drives ChatGPT.
10. Provider observes queue completion/blocking.
11. Provider captures a new completed assistant artifact.
12. Engine stores output, evaluates assertions, renders the next step, and repeats.
13. Final run is persisted and displayed.

## Failure handling

The following fail closed and end the workflow as blocked/failed without automatic retry:

- `message-delivery-timeout`
- `network-error`
- `rate-limit`
- `session-expired`
- `confirmation-required`
- `dom-unrecognized`
- `send-not-confirmed`
- `uncertain-send`
- `assistant-output-unavailable`
- `assistant-turn-not-advanced`
- `browser-session-interrupted`
- assertion failures

Queue blocking reason is preserved verbatim in the provider result when available.

## Testing strategy

### Unit

- DOM adapter output capture uses only the latest completed assistant turn.
- Previous assistant output cannot satisfy a new step.
- delivery timeout gets the specific reason.
- run repository bounds history to 20 and persists latest snapshots.
- controller refuses to start when the queue is busy.
- provider maps queue completion to `completed` with receipt/output.
- provider maps queue block to `blocked` without resending.
- interrupted persisted run becomes blocked on attach.

### Browser E2E

Use the existing deterministic fixture and real extension build:

1. Load a two-step workflow.
2. Run step 1.
3. Fixture completes with `architecture result`.
4. Assert step 2 prompt contains `architecture result`.
5. Complete step 2.
6. Assert workflow run becomes completed and both outputs are persisted.

Additional E2E:

- delivery timeout blocks the workflow as `message-delivery-timeout`.
- normal queued messages prevent workflow start.
- page reload mid-step never resends and persisted run becomes blocked.

## Success criteria

v0.2 is complete when a developer can load and execute a two-step FlowRun workflow in a real extension test, the second prompt consumes the first assistant output, run receipts are persisted locally, and all existing queue tests remain green with no new extension permissions.
