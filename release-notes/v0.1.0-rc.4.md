Fourth release candidate: releases are now cut by CI under a single enforced version contract, and the packaged assets are reproducible.

The extension itself is unchanged in this candidate. All four files in this ZIP are byte-identical to `v0.1.0-rc.3` (verified by SHA-256 over `background.js`, `content.js`, `icon128.png`, and `manifest.json`), so nothing here changes what the extension does at runtime.

Changes since rc.3:
- Publishing no longer happens by hand. Pushing a `v*` tag runs the **Release** workflow, which verifies the tagged commit, requires that commit to be an ancestor of `main`, requires a reviewed `release-notes/<tag>.md`, and publishes the ZIP plus its checksum from the artifact the verify job built — the release never rebuilds the extension (#12).
- `package.json`, `manifest.json`, and the release tag can no longer disagree: `npm run check:version` runs on every CI build and again against the tag before packaging. The RC convention is now explicit — tag `v0.1.0-rc.4` ships extension version `0.1.0`, because a Chrome Manifest V3 version cannot contain a prerelease suffix (#12).
- Release assets are reproducible. `scripts/package-release.mjs` stages the build with a fixed timestamp, refuses to package a build whose manifest references a missing file, reads the archive back to compare its contents, and writes the checksum. Rebuilding the same commit produces a byte-identical ZIP (#12).
- Pull requests and releases share one verification path (`verify.yml`), so a release can only contain a commit that passed unit/integration tests, typecheck, all three builds, and browser E2E (#12).
- The README now documents the version scheme and the release procedure, and the `FlowRun v0.1`–`v0.3` labels are clarified as workflow-runtime generations rather than extension release versions (#12).
